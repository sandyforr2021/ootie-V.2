# OOTIE AI Decisions

## D-AI-001 — Google Cloud is the only paid AI provider

The former third-party image provider is removed from the repository and is not retained as fallback. Styling, VTO and image preview are Google Cloud adapters behind one server contract. Google AI Studio / Gemini Developer API is not the formal provider.

## D-AI-002 — Provider details remain server-side

Vue knows Gateway operations, not model IDs. Project, model and region are Cloud Run environment. No Google credential, token or service account material belongs in browser code, request bodies or Git.

## D-AI-003 — Verified identity is authoritative

Gateway verifies the Supabase bearer token, resolves the OOTIE profile and re-queries clothing ownership. Client `userId`, `profileId` and `ownerId` are neither accepted nor trusted.

## D-AI-004 — VTO and outfit preview are different products

「虛擬試穿」 accepts one garment and uses Virtual Try-On. 「AI 穿搭預覽」 accepts multiple garment references and is labeled a visual simulation. Provider failure never silently changes mode.

## D-AI-005 — Private by default

Person and generated images live in a private bucket. Browser reads require matching Auth path ownership. A future OOTD publish action must be separate and explicit; generation does not make content public.

## D-AI-006 — Storage path, not generated Base64

Generated bytes are uploaded to Storage. PostgreSQL stores only paths, provider/model, generation type, item IDs, state, estimate, timestamps and error code.

## D-AI-007 — Charge prevention precedes provider call

The server kill switch, ownership validation, quota and generation-ID claim all run before inference. Image count/candidate count is one, output is 1K, and neither browser nor Gateway performs an automatic generation retry.

## D-AI-008 — Cloud Run uses keyless ADC

Production authentication uses a dedicated attached service account and metadata-server tokens. No service account JSON is required or accepted by the application repository.

## D-AI-009 — Remote setup is not paid-smoke completion

Passing tests/build and deploying Development infrastructure do not satisfy Live Smoke or Billing acceptance. Paid inference remains blocked until Project, Billing, remaining promotional credit, region, model, kill switch and quota have concrete evidence.

## D-AI-011 — Dedicated Development isolation

All new OOTIE remote work targets `OOTIE-personal-dev`; `OOTIE-sandy-dev` remains untouched because it contains unrelated workflow tables and disabled-RLS objects.

## D-AI-010 — Model lifecycle is operational work

VTO and image models are configured via env and isolated adapters. Review official lifecycle at deployment and quarterly. A model replacement must update adapter contract tests and docs without changing Vue components.

## D-AI-012 — Public URL is not public listing

Bookmark, Avatar and OOTD buckets may serve an exact public object URL, but anonymous or cross-member prefix listing is not allowed. Authenticated owners receive the minimum SELECT policy required by Supabase Storage replace/delete semantics. Cross-member DELETE returning an empty 200 response is treated as denial only after a follow-up read proves the object still exists.

## D-DEMO-001 — Demo data is deterministic and Development-only

The presenter account and supporting social graph are created by `scripts/seed-demo-data.mjs`. Stable deterministic IDs and upserts make reruns safe. The seed requires server-only Development credentials and refuses non-development Supabase targets; credentials are written only to the ignored `DEMO_ACCOUNT.local.md` handoff.

## D-DEMO-002 — Subscription is an explicit simulation

FREE, PLUS and PRO are product concepts behind `DemoPaymentProvider`. Subscribe, cancel and credit-pack actions write Development state and point transactions, but never collect card data, contact a gateway, create a recurring charge or claim that money changed hands.

## D-DEMO-003 — One points ledger, two independent controls

Subscription grants, promotional credits, birthday rewards and AI debits use the existing OOTIE point transaction foundation. VTO and outfit-preview costs are configurable server settings, not a permanent one-point-per-generation rule. Point balance does not replace the Google Cloud kill switch or the three-images-per-member daily quota.

## D-DEMO-004 — AI debits share generation idempotency

The Gateway claims a point debit using the same generation ID used by the AI ledger. A duplicate request cannot debit twice. Pre-provider validation failures do not spend points; once a provider request may have incurred cost, generation and transaction records remain auditable instead of being silently erased.

## D-DEMO-005 — Birthday rewards are private and annual

Birthday rewards are granted at most once per member per calendar year through an idempotent database function and appear in private transaction history. Date-of-birth data is never added to the public profile contract.

## D-DEMO-006 — Seed-only grants do not widen member access

Migration 021 grants Development seed CRUD on canonical saved outfits to `service_role` only. Authenticated member RLS and browser boundaries are unchanged; the grant exists solely to make the canonical Demo seed reproducible.
# Phase 3 decisions — 2026-10-01

- Follow and notification state is authoritative in Supabase; members have no local-only social fallback.
- Social notifications are emitted by database triggers and deduped by event tuple.
- External product import is a single authenticated server fetch. It does not crawl catalogs or bypass anti-bot controls.
- Inspiration stays separate from closet inventory until the member explicitly chooses 「已購買，加入我的衣櫥」.
- OAuth bootstrap creates only missing public defaults and never overwrites private profile data.
- Four authenticated SECURITY DEFINER subscription/points RPC warnings are intentionally retained because they are verified-user product boundaries. The unrelated RLS helper was removed from browser roles.
- Fresh or low-traffic indexes reported as unused remain until representative workload exists.
- Production deployment and Production configuration remain unauthorized.

# Phase 9 Production readiness decisions — 2026-10-02

- **D-PROD-001 — RED means no launch.** Planning, local rehearsal and Development hardening are allowed; Production resource creation/traffic waits for explicit cost and final release approval.
- **D-PROD-002 — Production Supabase is isolated.** Do not place Production in either Development project and do not copy n8n/workflow objects. A recurring-cost decision is required because the Free organization is at its two-project allowance.
- **D-PROD-003 — Development migrations are not a Production manifest.** Replace 020, exclude 021/023, review 022 and rebase 025 before a Production rehearsal.
- **D-PROD-004 — Free beta before real payment.** Production may launch later without a payment gateway; Development simulation RPCs/UI must not create payment claims in Production.
- **D-PROD-005 — Existing GCP AI project reuse is conditional.** Separate Production Cloud Run names, identities, secrets, logs, quotas and budgets are mandatory; n8n and Development OAuth architecture remain untouched.
- **D-PROD-006 — Backups require restore evidence.** Managed backup availability is not a completed backup strategy until an isolated restore drill passes.
- **D-PROD-007 — Public social metadata is server-rendered.** Production share pages cannot rely only on client-side SPA metadata for crawlers.
- **D-PROD-008 — User deletion is a designed workflow.** Never cascade-delete an account without a dependency/media/retention audit and legally approved anonymization rules.
