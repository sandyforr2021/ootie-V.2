# Free service memory protection

The owner received Render's memory-limit restart notice and observed HTTP 502. The service remains on Free (512 MB, 0.15 CPU); no upgrade or paid monitoring was enabled.

Changes: static files stream in 64 KiB chunks rather than full-file buffers; requests that read private images or JSON bodies share two active slots and at most sixteen waiting requests; disconnected queued requests are discarded; health and public HTML bypass this work queue. Shared image authorization and private-cache restrictions remain in place. Storage downloads have a 20-second timeout and stop collecting at 7 MB. WebP conversion runs one image at a time with native cache disabled, one worker thread and a maximum 2048 px derivative, preserving framing. Original files are unchanged. Browser private-image reads are limited to two at a time and the studio only hydrates the visible step/tab. Empty job polling slows to ten seconds and still never re-submits an uncertain generation.

Production start command: `MALLOC_ARENA_MAX=2 node --max-old-space-size=192 gateway/src/server.js`. The 192 MiB JavaScript heap limit leaves space for Buffers, native image processing and platform overhead. It is not a total-process memory cap or an availability guarantee. Runtime logs emit only RSS/heap/external byte totals and active/queued counts once per minute, without identifiers, tokens or photos. Use these logs for follow-up because Render's detailed memory charts require a paid plan.

`node scripts/check-free-memory.mjs` runs a separate local server with fake keys and both AI and the job worker disabled. It streams 48 images using eight parallel readers, checks health 48 times, and performs eight 4096 px WebP conversions. Observed local Windows peak RSS: 160 MiB; streamed 124 MiB; zero failed checks and zero paid API calls. This local result is not a measurement of Render production. The report is ignored under backups/free-memory-check.local.json. No test files are deleted.
